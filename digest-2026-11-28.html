张小龙《2019 微信公开课 Pro 版演讲》

本期范围从「现在到了微信十亿用户的关口」讲到「大家可能就不会做这个事情了」。主题：十亿用户关口：用户数不是重点；广州「附近」试点；下一个八年的挑战；做事要问「意义」而不是 KPI。

文字稿来源澎湃新闻整理的演讲全文，记者杨鑫倢、实习生柳童，2019-01-10 07:31 发布（演讲时间 2019-01-09 晚）。https://www.thepaper.cn/newsDetail_forward_2834574 （媒体整理稿，个别疑似笔误原样引用）

跳过本期范围内跳过小标题「总结」。该小标题只作结构参考，不单独讲，也不补讲。

原文

现在到了微信十亿用户的关口，我们一直不觉得用户有多少是特别重要的事情，或者说人口有多少是特别重要的事情。很多人总是会拿人口做一个指标来看自己的空间。我并不觉得是这样子的，微信目标从来都不是，我们的目标是要扩大用户数，如果扩大用户数在过去几年不断的推广，早一点把十亿人都覆盖到就好了。但是并不是这样子，事实上我们的用户数的增长是自然而然的过程而已。我们要考虑的是对我们已有的用户，我们现有的用户，我们能提供什么样的服务给他们，这是更重要的一个问题。因为人口总是有限的，但是服务才是层出不穷的。在过去十年算一个时代，但是自从互联网或者移动互联网出来之后，我有一个感觉三五年就算一个时代了。时代的更迭是更快了，它催生出来的需求也是更快了。围绕这种快速变化，我们实际上不用顾忌还有多少人口可以用，而是怎么样能够应对未来更多的需求。找到并且面对未来的需求才是在微信十亿用户关口所做的一个事情。

像在广州的用户，我们最近只给广州用户开通附近的店这样的入口，附近的餐厅，是在灰度发现里面，很多人并没有看到。去年在公开课说到，微信一部分是要探索线下的生活，这一块有点曲折，所以我们到现在还在一个灰度的阶段，目前只是团队拿广州用户做了一个试点。

类似这样的尝试会越来越多。因为我们自己发现，微信作为APP来说，虽然它已经承载很多很多东西，并且在承载这么多东西的情况下，看起来还很简单，但是毕竟它的承载能力有限。在下一个阶段，微信更多的是围绕微信，通过不同的APP尝试跟微信某种关联的其他的服务形态。像微信读书一样，如果把微信读书非要放到微信里面，看起来也可以，但是它可能作为独立的APP能够独立的进步，这样反而更合适。

很多人会问一个问题，微信下一步要做什么？今天花特别多的时间围绕微信的出发点来说清楚了微信过去是怎么做的，对于未来，这个时间可以面对微信的未来，刚好八年，也到了微信十亿用户，对我们团队来说在思考一个问题，微信开始面对下一个八年新的挑战。这个新的挑战不是来自竞争对手，而是来自于在用户层面，用户过去几年之后，每一年用户在变化，就像我刚刚说的三五年就是一个时代，我们要面对新的用户时代新的用户产生的需求。不管怎么面对这些需求，我觉得以微信做事风格，如果我们始终像过去微信一样，我们始终瞄准的是最好的工具，并且让创造价值的人体现价值，这样一个原动力做，我们再怎么走也不会走得太偏。

回顾这些年，自己看微信这些年改变了什么，我们自己还是挺有成就感的。你跟别人有什么不一样，当我们在思考问题的时候，思考做什么的时候，经常问自己一个问题，我们做这个事情的意义是什么。很多的团队做事情不问意义，而只是问KPI是什么，但是说老实话，微信团队从开始成立到现在，从来没有瞄准KPI工作过。但是并不妨碍团队能够越做越好。像小程序，如果围绕KPI去做，不知道怎么制定KPI，也没法制定KPI，围绕KPI大家可能就不会做这个事情了。

背景

  • 接着上一期讲第 24 期收在企业微信的「人就是服务」，最后一句是「关于企业微信就讲到这里。」本期进入文字稿里的「总结」部分。小标题本身跳过，正文从十亿用户关口讲起。

  • 这是他当时对「下一步做什么」的回答。演讲举办时，微信日登录用户已越过 10 亿。许多人会把这个数字当成终点或空间指标；他却把关口上要做的事，说成「找到并且面对未来的需求」，而不是继续把用户数做大。

  • 「附近的店」被他明确说成灰度试点。他提到，当时只给广州用户开通了附近的店、附近的餐厅这样的入口，放在灰度发现里，很多人并没有看到；并说线下生活这一块「有点曲折」，到演讲时仍停在灰度阶段。本期按他当时的表述来讲，不补写后来「附近」相关能力有没有扩大或改名。

  • 文字稿里的用词原样保留。如「微信目标从来都不是，我们的目标是要扩大用户数」，读起来像中途换了句法，按整理稿不改写。

核心观点

  1. 到了十亿用户，他仍不把用户数或「人口」当成最重要的指标。他说，很多人会拿人口来看自己还有多少空间；他并不觉得是这样。如果目标是扩大用户数，过去几年不断推广，本可以更早把十亿人都覆盖到。但用户数的增长在他看来只是自然而然的过程。更重要的问题是：对已经在用的人，还能提供什么样的服务。人口总是有限的，服务才是层出不穷的。

  2. 他把时代的切换，从「十年一个时代」改成了「三五年一个时代」。移动互联网出来之后，需求催生得更快。围着这种变化，不必再顾忌还有多少人口可以用，而要问能不能应对未来更多的需求。找到并面对这些需求，才是他所说的、在十亿用户关口要做的事。

  3. 广州的「附近的店」「附近的餐厅」，是他把「探索线下生活」继续往前试的一个例子。入口当时只对广州用户开通，放在灰度发现里，许多人并没看到。他回顾，前一年公开课已经说过，微信有一部分是要探索线下生活；这一块走得曲折，所以到当时还停在灰度，只是团队拿广州用户做试点。

  4. 类似的尝试还会更多，而且不一定都塞回微信这个 App 里。他的判断是：微信作为 App 已经承载了很多东西，看起来也还简单，但承载能力毕竟有限。下一个阶段，更多是围绕微信，用不同的 App 去做与微信有某种关联的其他服务形态。他拿微信读书作比：非要塞进微信里，看起来也可以；但作为独立 App 能够独立进步，反而更合适。

  5. 「微信下一步要做什么」在他这里，首先不是回答竞争对手，而是回答用户在变。他说，刚好八年，又到了十亿用户，团队在思考的是下一个八年的新挑战。这个挑战不是来自竞争对手，而是来自用户层面：每一年用户都在变化，三五年就是一个时代，要面对新的用户时代里新产生的需求。

  6. 面对这些需求时，他用来防偏的，仍是前面讲过的两个原动力。只要始终瞄准最好的工具，并且让创造价值的人体现价值，再怎么走也不会走得太偏。

  7. 思考做什么的时候，他要团队先问「意义是什么」，而不是先问 KPI 是什么。他说，很多团队做事情不问意义，只问 KPI；微信团队从成立到当时，从来没有瞄准 KPI 工作过，但并不妨碍越做越好。小程序是他举的反例：如果围绕 KPI 去做，不知道怎么制定，也没法制定；围着 KPI，大家可能就不会做这件事了。

对 PM 的启发

  • 规模到达一个整数关口，并不自动等于产品该换目标。十亿可以被看成空间已经用尽，也可以看成现有用户还在等更多服务。他选的是后者。对 PM 来说，先分清「还能够触达多少人」和「已经在用的人还缺什么服务」，是两件不同的事。

  • 增长如果只是自然结果，就不该倒过来变成日常工作的瞄准器。他承认，若过去几年不断推广，本可以更早覆盖到十亿人；但那不是他们的目标。把用户数当结果看，和把用户数当 KPI 去追，产品上会走出两条路。

  • 需求迭代加快之后，更值得盯住的是需求，而不是剩余人口。「三五年就是一个时代」不是一句情绪，而是在提醒：关口上要做的，是找到并面对新需求，而不是反复计算市场还剩多少人。

  • 灰度可以公开讲，而且可以讲成「还在曲折里」。他没有把广州「附近」讲成已经验证成功的新业务，而是说明年公开课就提过的线下方向，现在仍只在灰度、许多人并没看到。对 PM 更有用的，往往不是把试点包装成发布，而是先说清：在哪一类用户里试、入口放在哪、为什么还没有铺开。

  • 主产品变厚之后，新服务不一定要继续堆进同一个容器。微信读书的例子说明，看起来能放进去，不等于就应该放进去；有时独立出来，反而能自己进步。问「这个能力该不该做」，还要再问「它该不该继续做在现在这个 App 里」。

  • 「下一步做什么」可以先把竞争者放下，把原动力留下来。他用来校正方向的，不是对标谁，而是两句已经讲过的话：做最好的工具，让创造价值的人体现价值。新需求会变，用来判断偏不偏的尺子可以先不换。

  • 有些事一旦先写成 KPI，就可能根本不会被启动。小程序在他看来就是这类工作：围着 KPI，既不知道怎么定，也可能因此没人做。先问意义，不是反对衡量，而是避免只用测得动的指标，去决定一件还测不明白的事该不该做。

Personal Agent 大火，产品经理如何构建？张佳的AI实战笔记

人人都是产品经理，作者张佳的AI实战笔记（文末标注微信公众号：喜新），2026-11-27。

依据已读完该文全文。这是一篇把 Anthropic《Building always-on agents》、LangChain《What We’ve Learned Building Proactive Agents》、Langfuse《Evaluating proactive agents》，以及 DeepSeek Harness 团队《Super-agent 设计探索：迈向更自主的 Agent 系统》对齐起来的整理，给产品经理讲主动型 Agent 该怎么理解。作者在文首提到，字节刚发布 Personal Agent 产品「小豆」，腾讯、阿里也有组队开发的传闻；他强调，本文要对齐的是工程与产品结构，不是评测这些新产品。以下按作者对上述来源的转述来写，不把未在本文展开的工程细节补进去。

核心观点

  1. **他要把关键词从 Personal 换成 Proactive：主动干活。** 文中转述「Today 的产品负责人」用过的一个词：非托管任务。也就是说，它不像 WorkBuddy、豆包工作那样，需要用户打开客户端、创建工作区、准备资料再下达任务；安装注册之后，它应自己去找活干。有人会把它理解成「更多的定时任务」；作者认为这样太粗糙，因为定时任务仍要人花精力去安排，这就不叫主动。他给出的可靠路径是：自己探索可见上下文，建立触发事件，等待被触发，再决定要不要作业、要不要给用户推送。主动性是它自己构建的，接到的任务可以理解成「成为一个 helpful Proactive Personal Assistant」。

  2. **这些结构不只属于 Personal Agent。** 他判断，它们一定会被内化到办公 Agent、连接器和 Skills 里。交互入口会从输入框变成事件，记忆从聊天记录变成用户画像，界面从聊天变成任务列表，交付从「给答案」变成「替你动手」。做客服、审核或内部工具时，人也迟早会问：为什么每次都要重新说一遍，为什么不能自己发现、直接办好。所以，即便不是在做 Personal Agent，也该先搞明白：主动不是加一个推送，也不是加一组定时任务。

  3. **一直在线的不是 Agent 本身，而是外围的 Harness。** Agent 大部分时间在「睡觉」，有事发生才醒一次：要么继续历史任务，要么在一个新会话里把事做完，交付后再睡。常规 Agent 是「打开、开会话、干活」；Personal Agent 是「事件触发、干活」。事件可以是位置变了、到时间了、用户点开了某篇内容，或运动数据更新。真正难的是事件同时到来时怎么办：挨个做还是并行，做完是一条一条发还是先攒住，前置上下文去哪找，以及该用一个大管家还是为每个事件单开一个 Agent。作者写道，Claude、DeepSeek、LangChain、Langfuse 面对这些问题，给出的方案大差不差。

  4. **干活这一层，他着重讲了「先收住，再决定是否打扰用户」。** Claude 的做法是先把事件放进「收件箱」，由 handler 判断要不要做，要做再激活 worker；worker 干完后，结果不直接发给用户，而是先进入「发件箱」，避免用户被连续或同时到来的反馈淹没。DeepSeek 则是程序先筛选事件，符合条件的交给 Router 判断要不要派发给 Worker，Worker 做完再回到 Router，然后才转给用户。若再加一个「闹钟」，让用户和 Agent 都能配置确定要定期重复的任务，主动型在他看来就大致成形了。

  5. **「该不该做」比「怎么做」更重要，否则账单会炸掉。** 这个判断也不该再退回给人，否则又变成托管式办公 Agent。DeepSeek 的 SuperAgent 是两层：先用程序按规则决定要不要把事件交给 Router Agent，再由 Router 审视要不要往下派。文中举例，一个盯飞书和 GitHub 建议的原型，程序规则可以简单到「谁发的消息」「有没有 @ 我」，再加上 Router 的提示词。Langfuse 更强调默认不干，只有「干完值得打扰一下用户」的事才动手，并写过「Being too eager or going too far is a core risk」。做到什么程度，他们分成四档：通知、建议、请示后做、直接做；越贵、越不可逆，门槛越高。作者把「不要把凭证直接交给 Agent」视为产品经理本就该有的常识，对 Claude 文中的权限经验则一笔带过，没有展开。

  6. **上下文和记忆，在他看来几乎是同一件事，而且比办公 Agent 更难。** DeepSeek 用 Thread 来组织：同一个 IM 话题、同一个 PR、同一封邮件下的连续事件算一条 Thread；Router 为它创建 Worker 后，后续事件直接进这个 Worker，不再经过 Router，Worker 也可以去查这条 Thread 的历史。进入 Worker 的上下文分两层：近期、强相关的直接内联，长内容只给引用，需要时再按 ID 展开。LangChain 的经验是，每个 Agent 醒来都是空状态，再通过连接器从记忆里临时拼接上下文。Claude 则把任务上下文和记忆放在同一层级，用文件来存：instructions.md 放指令，notes/ 放关于用户的信息，progress/ 放任务进度，reported.md 放已经说过的话；每次运行先加载索引和指令，具体笔记按需再读。LangChain 和 Claude 都提到过「晚上做梦」：夜里激活一个任务，审视当天的任务、决策、动作、交付和反馈，再整理记忆。作者认为，具体整理什么，目前主流做法和两三年前的开源项目还差不多。文末他还记下 DeepSeek 的三点，认为做 Personal Agent 时同样值得借鉴：工具调用改成异步，后台执行时仍能收新消息；先在后台准备，有价值再交付，没有就丢弃；在主系统外放一个独立的 Watchdog 会话，定期检查 Worker 有没有进展、方向有没有偏。

  7. **他的总结是：这套东西并不神秘，也没有新理论。** 盘完之后，Personal Agent 和前一阵很热的 Harness 工程并没有本质区别，仍然是把传统工程实践用到 Agent 上。他引用 DeepSeek 在 SuperAgent 设计结语里的话：回顾整套设计，并没有提出全新的理论，而是把计算机系统里经典的工程思想，用到了 Agent 系统的构建中。需要说明的是，作者开篇列了七个问题，后半关于「它怎么越用越懂你」「凭什么敢替你动手」「该在哪儿、说多少」「你怎么知道它做对了」，在正文里没有各自单独成节，而是收在上下文、权限和收件/发件这些部分里。本期按原文实际写到的内容来讲，不补写他没有展开的部分。

对 PM 的启发

- **「主动」如果还要靠人去布置定时任务，产品形态就还没有换。** 先问它能不能自己发现事件、决定做不做、再决定吵不吵用户，比先问它会不会聊天更重要。 - **Always-on 是基础设施问题，不是让模型 24 小时保持对话。** 大多数时间它在睡，醒过来是因为事件到了。产品要设计的，是唤醒条件、并发时怎么排，以及结果先放到哪里，而不是把输入框一直开着。 - **默认不做，往往比默认都做更像一个完整的产品决策。** 「该不该做」会直接变成账单、打扰和风险；通知、建议、请示后做、直接做，四档应对应不同的代价和可逆性。 - **上下文不能指望用户每次重新喂一遍。** 同一条 Thread 里的后续事件、该内联还是只给引用、已经对用户说过什么，都要先有地方放。记忆整理可以放在夜里，但整理规则本身仍是产品要写清楚的部分。 - **结构可以先用经典工程来搭，不必等待一套全新理论。** 收件箱和发件箱、路由和 Worker、Watchdog，都是旧思想。对 PM 来说，更需要先把这些结构翻译成用户能感知的行为：它什么时候出现、出现时带了什么、失败时谁来看。

Product management is about decisions, not just deliveryDebbie Blanchard

英国教育部数字、数据与技术团队（DfE Digital, Data and Technology）博客，作者 Debbie Blanchard，2026-11-24。

依据已读完该文全文。这是作者在一次产品经理社区外出讨论后写下的实践整理，讨论对象是已有大量数字服务、问题和团队边界并不重合的组织。文中例子来自政府部门，但讨论的是决策质量、路线图、可逆性和跨团队的用户旅程，并不只适用于公共部门。

核心观点

  1. **她把产品管理的价值，放在「帮助组织做出更好的决策」，而不只是把东西交付出去。** 开篇的问题是：当答案并不总是再做一个新产品时，好的产品管理是什么样的。教育部这样的组织，工作常常跨越已有服务、平台、政策、数据和组织边界，问题并不总是刚好落在一个产品或一个团队里。社区讨论里反复出现的一句话是：产品管理通过帮助组织做出更高质量的决策来创造价值，而不只是通过交付物。

  2. **产品经理要帮组织选择：哪些问题值得被处理，要改变的是什么结果，已有哪些证据，假设是什么，有时还包括该不该做。** 这些问句在不是从一张白纸开始时更重要。对一个服务的决定会影响另一个服务；新做一个东西，就意味着以后还要运营和维护它；改善旅程中的一段，并不自动改善整段旅程。

  3. **正因为如此，她提醒要小心使用路线图。** 交付计划仍然重要，团队需要知道承诺、依赖和日期。但路线图不该只告诉大家准备造什么，而应让人看见：想改变的是什么，为什么相信这样做会有效，这背后有哪些证据和假设，以及什么情况下应该改道。把路线图上的每一项都做完，如果结果没有跟着来，也不算成功。路线图应帮助做出和重新审视选择，而不是把早先的假设变成一份必须捍卫的承诺。

  4. **更好的决策，意味着先问：什么证据会让我们改变主意。** 她列出的问题包括：要改变的结果是什么，已有哪些证据，假设是什么，为什么是这个方案、为什么是现在，如果什么都不做会怎样。测试的目的不是证明原来的想法是对的，而是降低不确定性，让下一个决策更好。这件事还有另一面：只要求产品经理去挑战是不够的。如果希望人们把不确定性摊开、质疑既定计划、把难的取舍讲清楚，领导者就需要提供一个可以建设性提出异议的环境。不能一边要求人们运用判断，一边让审慎的质疑在职业上变得危险。

  5. **不是每个决策都需要同等分量的审查。** 他们用了一个比喻：帽子、理发和纹身。帽子便宜、容易拿下来，可以先戴上，不行就换；理发选错了也能恢复，但要花一点时间；纹身则后果更大、更贵、更难逆转。原则是：证据和挑战的强度，应匹配这个决策的后果和可逆性。一个小的、可逆的实验，不必先做几个月调研；一个会影响多项服务、带有纹身级后果的昂贵承诺，也不该只建立在帽子级的证据上。他们要的不是完美确定性，而是在现有证据下做出有意识的决定，并说清：什么情况下继续，什么情况下转向，什么情况下停止。

  6. **用户经历的是旅程，不是组织结构。** 他们特意拿政府服务之外的例子来讨论：一次本该很直接的伦敦共用出行。可用性、预订、换乘、地理围栏、停车、移动网络，再加上手机电量越用越少，每一段单独看都能解释，合在一起，旅客还是误了车。旅客遇到的是一个旅程问题。政府服务也是如此。用户不必知道每一段分别由哪个团队、哪项服务或哪个司局负责。每个团队都可以在自己的边界里做出完全合理的决定，合在一起却仍给用户一次糟糕的体验。因此产品经理需要看到自己产品的前和后：共享的结果是什么，哪些能力、研究、数据或学习可以复用，而不是再造一遍。没有任何一个专业独自拥有用户的声音；研究、设计、技术、分析、交付、政策和运营都会碰到问题的不同部分。更好的决策，发生在这些视角一起围着结果讨论的时候。

  7. **优先级本身也是一种决策，而且必须在有权做决定的那一层做完。** 很多事情可以同时显得重要，但排优先级不是承认它们都重要，而是决定哪些不会发生，或至少现在不做。如果相互竞争的优先级没有被解决，取舍并不会消失，它只是被推到更下面、没有权限做了断的团队那里。产品经理可以让取舍被看见，拿出证据，说明机会成本，以及一项新承诺对已有结果意味着什么；但产品管理不能代替组织自己做优先级选择。更好的决策，需要发生在对的层级，由同时拥有权限和证据的人来做。

  8. **她把当天的方法收成三句话，以及一条简单的链。** 挑战假设：把要改变的结果、已知、假设，以及什么会让我们改变主意，说清楚。用已有证据做决定：把取舍摊开，不要等待可能永远等不来的确定性。从发生的事情里学习：衡量的是结果有没有改变，而不只是功能有没有交付，并愿意改道。模型是：Outcome → Hypothesis → Evidence → Decision → Learning。这些很少能在隔绝中做好。它依赖产品、设计、研究、技术、交付、数据、政策和运营把不同证据带过来，依赖领导者做出选择并提供可以质疑的条件，也依赖团队主动看到自己边界以外的地方。流程和治理可以帮忙，关系同样重要。他们需要留出空间，让有人能够说：「我还不确信这是该做的事。我们能不能再看一遍证据？」产品管理不只是让路线图发生；最好的时候，它是帮助一个组织一起，就结果做出更好的决定。

对 PM 的启发

- **先问这个决策要改变什么结果，再问要不要再做一个功能。** 把路线图上的项做完，如果结果没跟上，并不等于这季度是成功的。 - **路线图应把假设和退出条件写在明处。** 它不是一份必须捍卫的承诺清单，而是帮助团队在证据变化时重新做选择。 - **审查的重量要跟可逆性匹配。** 帽子级的试验用纹身级的论证，会把速度拖死；纹身级的投入只用帽子级的证据，则是在用组织付账。 - **用户不会按你的组织图走路。** 每个团队在自己边界里都做对了，整段旅程仍可能是错的。产品经理要看自己这块的前和后，以及哪些东西可以复用。 - **没有被做掉的优先级，会落到没有权做决定的人身上。** 产品经理可以把取舍讲清楚，但不能代替该做决定的那一层去决定「什么先不做」。 - **「什么证据会让我们改变主意」应被当成一个常规问题来问。** 若提出这个问题在组织里会有职业风险，缺的就不是框架，而是做判断的条件。
