张小龙《2019 微信公开课 Pro 版演讲》

本期范围从「回到朋友圈这里，说一下朋友圈社交相关的」讲到「但是在手机里发是实时，是亲身经历的东西」。主题：推特与「你在做什么」——PC 时代与手机端的差别；人是环境的「反应器」；真实记录而非回忆。

文字稿来源澎湃新闻整理的演讲全文，记者杨鑫倢、实习生柳童，2019-01-10 07:31 发布（演讲时间 2019-01-09 晚）。https://www.thepaper.cn/newsDetail_forward_2834574 （媒体整理稿，个别疑似笔误原样引用）

原文

回到朋友圈这里，说一下朋友圈社交相关的，先回顾一下历史。推特是一个很伟大的产品，在座大部分人可能没有用过。它影响后来很多产品的形态，比如说微博。我记得在微博的时候，包括腾讯也做过微博，在输入框发一个东西的时候，输入框里面会有一个提示，你们还记得它提示什么吗？是你在做什么，还是你在想什么？它提示你在做什么的举手。提示你在想什么的举手。剩下的都是看不到提示的。

这是一个很有意思的话题，推特、微博是在PC时代的东西，如果它问你你在做什么，你肯定是在敲键盘，因为你没有别的事情可以做，你正在输入，他只能问你正在想什么。但是我们仔细想一下，如果要记录正在发生的事情，你不能说你在想什么，而是应该说你在做什么，或者你看到了什么。那个时候在电脑上是看不到这些的，所以只能是在想什么。

这是微信和之前很多应用本质的区别，微信是一个手机APP，并且我们并不需要有很强的PC客户端，所以它是一个手机APP，是跟着你走的，并不是电脑放在那里，你只能去看他，所以在电脑上不会摇一摇，在微信里会有摇一摇这样的东西，因为你是摇不动一个电脑的。这是一个很大的优势。

手机端APP是可以记录你在做什么。比如说走在路上拍一个照片发出去，这是你在做什么，我走在路上看到这个东西我给它拍一个照片，但是在电脑前只能说我在做什么，我在整理我的照片，把昨天的照片发到电脑里去。这是有本质的不同。很早以前我说过一句话，人是环境的反应器，你遇到什么样的环境，你就会有什么样的反应。

纯粹的反应器是低等动物，你触他一下他动一下。对人来说，虽然是高等动物，但是还是有这样一个基因在里面，他是受环境的影响，但环境是什么，你就会怎么样想问题。如果你坐在电脑前面，电脑就是你的环境，或者说你在电脑里看到的信息就是你的环境，所以你在电脑里面输入一些什么东西，往往都是在电脑里面看了一篇文章，所以想输入对文章的读后感。环境就是电脑或者里面的文章，所以只能对这样一个环境做出反应。

但是拿着手机，你的环境是真实的环境，这个时候做出的反应也是对真实环境的反应。这个时候你的记录是真实的，而不是想象出来的，你不是在回忆，而是在经历。这样就很有意思，你同样是发一个信息，如果发到一个电脑里面类似微博的东西，你在回忆，你在记录想法。但是在手机里发是实时，是亲身经历的东西。

背景

  • 接着上一期讲第 15 期停在「朋友圈和相册是两个概念，只不过不小心混在一起了」。中间跳过致谢和玩笑之后，他回到朋友圈，开始从产品史的角度讲：这个功能到底在记录什么，以及手机和电脑为什么会让人发出完全不同的东西。

  • 「推特」「微博」在这里是作为产品形态来讲的。他说推特影响了后来很多产品，包括微博；也提到「腾讯也做过微博」。本期只按他当时的讲解记录，不另作产品史核对。

  • 文字稿里的用词原样保留如「PC时代」「手机APP」，以及「他只能问你正在想什么」「你只能去看他」里的「他」。

核心观点

  1. 他先用一句提示语，把两种产品立场分开。推特在他看来是一个很伟大的产品，影响了后来许多产品的形态，比如微博。他问在座的人：在微博（包括腾讯做过的微博）的输入框里发东西时，提示写的是「你在做什么」，还是「你在想什么」？

  2. 在电脑前，「你在做什么」问不下去。推特和微博是 PC 时代的东西。人坐在电脑前，正在做的就是敲键盘、正在输入，没有别的事情可做，所以产品「只能问你正在想什么」。可如果目的是记录正在发生的事情，就不该问你在想什么，而该问你在做什么，或者你看到了什么。那个时候在电脑上是看不到这些的，所以只能落成「在想什么」。

  3. 微信和他前面说的许多应用，本质差别在于它跟着人走。微信是手机 App，而且并不需要很强的 PC 客户端。电脑是放在那里、人走过去看的；手机是跟着人走的。所以电脑上不会有「摇一摇」，微信里会有——「你是摇不动一个电脑的」。他把这看成一个很大的优势。

  4. 同样是「发一张照片」，在路上和在电脑前，记下的不是同一件事。走在路上拍一张照片发出去，这是「你在做什么」：我走在路上看到这个东西，给它拍一张。坐在电脑前，往往只能说：我在整理照片，把昨天的照片发到电脑里去。他说，这有本质的不同。

  5. 他用一句话收住这个差别：人是环境的「反应器」。很早以前他就说过，人遇到什么样的环境，就会有什么样的反应。纯粹的反应器是低等动物，「你触他一下他动一下」；人虽然是高等动物，但仍然带着这样的基因，会受环境的影响，环境是什么，就会怎么样想问题。

  6. 坐在电脑前，环境就是电脑，或者电脑里的那篇文章。所以人在电脑里输入的东西，往往是刚看完一篇文章之后的读后感——只能对这样一个环境作出反应。拿着手机时，环境是真实的环境，作出的反应也是对真实环境的反应。这时的记录是真实的，而不是想象出来的：你不是在回忆，而是在经历。

  7. 于是，同一条「发信息」，在两种环境里不是同一种行为。发到电脑里类似微博的东西，你是在回忆，在记录想法；在手机里发，是实时的，是亲身经历的东西。

对 PM 的启发

  • 输入框里的一句提示，往往已经假定了用户处在什么环境里。「你在做什么」和「你在想什么」不是文案风格的差别，而是产品认为人此刻能看见什么、正在经历什么。写提示语、写默认引导之前，可以先问：用户当时到底站在哪里？

  • 把电脑上的产品搬到手机上，如果没有改掉对「环境」的假定，就还是旧产品。他的对比很具体：电脑前整理昨天的照片，和走在路上拍下眼前的东西，看起来都是「发一张图」，记下的却不是同一件事。

  • 功能要跟人所在的环境匹配，而不是跟「别的产品也有」匹配。「摇一摇」在电脑上没有意义，因为人摇不动电脑；它出现在微信里，是因为手机跟着人走。一个功能值不值得做，可以先看它是不是这个环境里才成立的反应。

  • 「人是环境的反应器」是一个很好用的设计假设。人写下什么、拍下什么，很大程度取决于当时周围是什么。做记录、分享、动态类功能时，与其先规定用户该生产什么内容，不如先看产品把人放进了什么样的环境。

  • 「正在经历」和「事后回忆」是两种不同的产品工作。前者要让人在真实环境里立刻记下反应，后者是对着已经过去的材料整理想法。两者都可以做，但不宜用同一套交互去混。

对谈 MiniMax Code 负责人：什么是有价值的 Personal Agent？人人都是产品经理／特工宇宙

人人都是产品经理，作者特工宇宙，2026-11-18。文中写明，这是 2026 第二届观猹大会现场对 MiniMax Code 研发负责人 Ronny 的 AMA 对谈整理。

依据已读完该整理全文。文中关于内部代码由 AI 完成初稿的比例、token 效率实验结论，以及同事用产品做小程序的例子，均来自整理者转述的 Ronny 陈述或现场举例，本期不另作独立核实。文末「什么是有价值的 Personal Agent」一段是整理者的收束，与 Ronny 的陈述分开写。

核心观点

  1. **写代码变容易了，变难的是审阅和长期维护。** Ronny 说，他们自己在用 MiniMax Code，并把它当成一条严格标准：Agent 要能开发自己，完成软件意义上的自进化；每个人都要用它，发现不顺滑的地方再改掉，让自己成为第一批用户。比例上，他称 95% 以上的代码、甚至文档，可能都是由 AI 编写的，过程中还会用多个 Agent 做 Review。写代码本身越来越简单，但「怎么样审阅、检查代码，并保证代码架构能长期维护」变得更难：生产被 AI 接走了，质量控制和架构决策的成本反而上来了。

  2. **用 AI 写代码，最根本的坑往往不在模型，而在人。** 他觉得很多人是「脑子里面知道自己要干什么，但就是表达不出来」，所以第一步是先向 AI 澄清意图，需要很多来回；他常用一个 Skill 反过来拷问自己：这件事为什么要做、ROI 是什么、有哪些决策要提前做。第二步是审阅方案。他看到一种不好的习惯，是当甩手掌柜，需求扔过去就不管，等 AI 干完再看结果；中间少了一步：AI 给出技术方案之后，人要审阅、评论，判断哪个方案在当下最合适，然后做明确的决策，「这个过程很重要，不能完全交给 AI」。第三步是控制交付的颗粒度。AI 动不动写出几万行，人根本没法看；以前这种情况也不被允许，所以要把修改拆成最小原子化单元，确认最小的一步成功了再往前推进，出了问题能回退。

  3. **榜单上的一次性完成率，不够用来衡量软件工程。** 被问到这些 Skill 会不会被模型内置时，他认为经典软件工程的范式是公开信息，模型将来可以学到；但现在很多开源榜单看的是一次性任务的完成率，而软件工程要的是可扩展、可维护、能持续生长的东西。所以仍然需要给 Agent 设护栏，让它不是只把这个需求做完。

  4. **Harness 被他看成一门实验科学。** 他所说的 Harness，是 Agent 循环外面套上的工具、提示词和上下文管理；循环里最核心要治理的是 context，既要避免「爆炸」，又不能让任务完成率掉下来。业界有一阵在讨论用写代码的方式编排工具，他们没有「无脑跟」，而是把主流方案都试了一遍。他给出的结论是：用 TypeScript 在 QuickJS 沙箱里编排多个工具，再配上好的工具检索，可以做到 token 效率提升 15% 以上，同时任务完成率不掉。这个数字是他陈述的实验结果，本期不作核对。他常对团队说，要「本着做化学实验的态度」去做 Harness：不是有一个好想法就一定要上，而需要系统的论据。

  5. **只把代码写对，还不够。** 在他看来，现在的 Coding 产品多半还在解决最基础的问题——怎么一次性把代码写对；还没解决的是，在整个软件工程生命周期里，人还要管理需求、在多个任务之间切换，心智负担仍然很重。所以他对 MiniMax Code 的理解是：它不仅要帮人写好代码，还要帮人管好事情，有点像工作和生活里的一个 PMO，能管进度、主动提醒，把心智负担解放出来。再往下一层，是人和人的协同，将来会变成「你的 AI 和我的 AI」之间的协同，需要分享文件、上下文和会话的基建。他说，如果 AI 只是 for 工作或者 for 代码场景，它会让人变得更累；Personal Agent 的价值，是让人真正感觉到这个时代因为 AI 变得更好。

  6. **自我进化仍然要有人在回路里。** 被问到 RSI（自我迭代）时，他强调自己理想中的自我进化「仍然需要 human in the loop」：公司里每个职能的人都在用这款 Agent，提交正反馈和负反馈，再由做模型和做 Harness 的人吸收、优化。Harness 会随模型变强而变薄、变标准化，但不会消失，因为它是模型和物理世界交互的桥梁。能标准化的部分，他觉得会像当年「让模型稳定输出结构化数据」那样，最后被训练进模型，变成底层能力。

  7. **Work Agent 不必另起炉灶；软件应为个人定制。** 他认为 Work Agent 和 Coding Agent 不应该分开：上一个时代人们用代码重建了工作，所以 Coding Agent 本身就是通用 Agent 的底座，Work Agent 应该在这个底座上进入具体场景。他举了两个内部例子：一位不会写代码的同事，不到一个下午就做了一个可以连接手机做 Phone Use 的小程序；另一位同事觉得微信公众号预览体验可以优化，就让产品直接生成了一个改进预览的 Mini App。他的判断是：原来是一小部分产品经理代表很多人的需求去做一个产品；现在应该是一小波人把舞台搭好，让大家的 AI 去实现各自的需求。「软件本身就应该不再是为一个行业定制，软件就应该为你私人定制。」

  8. **整理者的收束。** 文末把 Ronny 的观点收成一句：一个只会把代码写得更快的 Agent 还不够，它还要适应你的工作方式，帮你管理需求、切换任务、跟进进度；判断仍由人来做，但不必事事都盯着。「AI 做得更多，人操心得更少，才是 Personal Agent 真正的价值。」

对 PM 的启发

这篇文章最值得拿走的，不是又一个 Coding Agent 的能力清单，而是一套仍然把人放在决策位置上的用法。需求扔出去等结果，看起来快，却把最关键的方案选择交出去了；AI 越能一次写出很长的东西，越需要把交付拆到人还看得完、出了问题还能退回的粒度。对「个人助理」类产品来说，只加速生产是不够的，还要看它有没有把需求、任务和进度这些消耗精力的事接过去，同时把判断留在人这里。

核心观点

  1. **作者先从一个很具体的感受写起：否定往往不带出路。** 他写自己最近一个月在用插件生态接客户的个性化需求，已经上线了假期余额、每日出勤、工资追算器等插件。过程中听到两种意见：有朋友说这些插件「只是解决现有客户的需求，没什么意思」；有研发同学担心数据接口一旦开放，「就会被客户随意用 AI 调用，我们的服务器就崩了」。作者的观察是，这两句话里都没有解决方案——不告诉你怎样才有意思，也不告诉你怎样才不会崩。评价别人的方案「是世界上最廉价的事。说 No 的成本，是零。」

  2. **陈安妮的规则是：对方案只能说 YES 和 Hope，不许说 No。** 据整理，YES 是这个方案好的地方，Hope 是希望它往哪个方向调整。采访者问，如果真的不喜欢某个方案又不能说 No，怎么办？陈安妮的回答是「忘掉它」。采访者又问，能不能说「YES，但我 Hope 这个方案不要做」，用 Hope 夹带一个变相的 No？她的回应是：「只要说你想要什么就好了，没必要说你不想要什么。」在这套机制里，所有方案放在一起，YES 和 Hope 得票多的继续推进，排序靠后的自然淘汰。作者特别点出：淘汰的是方案，不是提方案的人；传统公司里，「这想法不行」听着听着，就容易变成「这人不行」。

  3. **红线仍然可以直接说 No，但最好同时给出「怎样才行」。** 作者写明，合规、安全、资损这类问题必须允许直接说 No；可即使在这里，最好也顺手给出路径，否则说的就不是风险，只是拒绝。

  4. **一个安全的表达格式，会改变人愿不愿意继续提方案。** 整理转述陈安妮的例子：设计团队给 Livo 出了 10 个图标方案，产品同学整体不满意，又怕打击积极性，憋着没说。套上这套机制后，有人说色彩很喜欢（YES），但希望它更能体现产品内核（Hope）；设计师觉得自己的巧思被看见了，第二天做了接近 100 个方案。陈安妮的原话被转述为：「因为他觉得自己设计的巧思被肯定、被看见了。」

  5. **作者把开头那两种声音，翻译成了 Hope。** 对「没什么意思」，他的改写是：用 AI 接住客户点名要的需求，这个起点比追新概念扎实，希望这些插件跑通之后，能沉淀出做插件的方法论。他承认自己也走过弯路：最早想一步做成「HR 工作台」，功能越列越多，一个人做不完，项目无疾而终；后来先把「没意思」的插件一个个做出来，工作台反而自己长了出来。他的判断是：有意思往往是跑通之后的副产品，不是否决跑通的理由；客户愿意付费的需求，恰恰是最真实的需求。对「服务器就崩了」，他译成：你确实需要这个接口，希望带上限流、配额和权限白名单再开放。同一句担忧，说 No 是一堵墙，说 Hope 是一份需求文档。他还写到，很多 No 底下其实埋着一个 Hope——「没预算」「没人」「服务器会崩」，翻译过来都是「我希望有更多资源」；说困难是安全的，提要求是有责任的。YES and Hope 的另一个价值，就是把这个埋着的 Hope 逼到台面上。

  6. **做 AI 产品尤其需要这套机制，因为非共识的东西一开始都看起来不靠谱。** 作者认为，AI 产品的 Demo 常常数据没跑通、体验毛糙、偶尔幻觉或宕机，用现在的标准去评，几乎一定不及格。所以每一句 No 的命中率看起来都是 100%，但 No 用的是现在的标准，杀死的是未来。Hope 则允许人「用未来的标准说话」。他还转述，快看要做的 Livo 被陈安妮形容为「实时活着的 AI 世界」，放到传统评审会上，第一句话大概就是 No。陈安妮的原话被转述为：「说出来别人可能觉得有点离谱——我们依靠群体智能。」作者的判断是：如果内部 No 文化盛行，这样的产品不会死在市场上，而会死在自己的会议室里。

  7. **这套机制要跑起来，leader 得先少拍板。** 作者转述，陈安妮过去是什么都要拍板的人，现在更像「给大模型提 Query 的用户」：只提问题和需求，最后在投票之外做一点加权。如果只学了「不许说 No」，没学「领导先不拍板」，Hope 用不了多久就会变成新的、更虚伪的 No。他的收尾是：AI 转型时真正稀缺的不是判断力，而是让那些看起来不靠谱的可能性，活到能被认真评估的那一天；这套机制给每句反馈加上了一个硬性成本——你得带着出路来。

对 PM 的启发

可以先把「说 No」和「指出风险」分开。指出风险而不给出路，评审会上会显得很正确，却也可能让还不够完整的方案过早死掉。把反馈改成「好在哪里」和「希望它怎样改」，并不等于放弃标准：合规和安全仍然可以直接拦住，但拦的时候最好同时说清怎样才行。对做 AI 产品的团队来说，Demo 阶段看起来不靠谱几乎是常态；如果组织里只允许用现在的完成度投票，非共识的方向很难活到被认真评估的那天。
